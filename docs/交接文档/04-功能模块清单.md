# 04 — 功能模块清单（含设计与实现）

> 本文档详尽描述每个已实现功能的设计思路、实现方式、入口和数据表。按功能域组织。

## 一、平台与多租户

### 1.1 登录鉴权

**设计**：三端统一鉴权体系，JWT Token 模式。登录时验证账号密码后生成 Token，前端存入 sessionStorage，后续请求通过 Axios 拦截器自动携带 `Authorization: Bearer <token>`。Token 内包含：userId、tenantId、userType（platform/booth/tenant）、permissions。

**实现**：
- 后台登录：`LoginController` → `/auth/login`，支持验证码（sys_auth_code 表）
- 岗亭登录：复用同一接口，userType = booth
- 小程序登录：`MiniAuthController` → 微信 code 换取 openId + 自动注册 wx_user

**关键类**：`LoginService`、`AuthService`、`TenantContext`（ThreadLocal 存储当前请求的用户/租户上下文）

**表**：`sys_admin_account`、`sys_login_log`、`sys_auth_code`、`wx_user`

### 1.2 多租户数据隔离

**设计**：基于 MyBatis-Plus `TenantLineInnerInterceptor` 自动在 SQL 追加 `AND tenant_id = ?`。租户 ID 从 `TenantContext`（ThreadLocal）读取，禁止从前端参数获取。三种用户类型：
- `platform`：tenantId=null，跨租户访问所有数据
- `booth`：tenantId=null，岗亭管理员跨租户
- `tenant`：tenantId 不为 null，限制为本租户数据

**实现**：`JushanTenantLineHandler`（实现 `TenantLineHandler`）控制哪些表跳过租户拦截，`JushanTenantLineInnerInterceptor` 负责 SQL 自动拼接。全局表白名单（IGNORE_TABLES）定义无需租户过滤的系统表。

**关键类**：`JushanTenantLineHandler`、`TenantContext`、`JushanTenantLineInnerInterceptor`、`MybatisPlusConfig`

### 1.3 管理账号 CRUD + 密码重置

**设计**：后台账号归属租户/公司/部门，创建时自动生成随机密码。密码重置为常见管理操作。权限通过角色分配（sys_admin_account_role 中间表）。

**实现**：`AdminAccountController` → `/api/v1/admin-accounts`，标准 CRUD + 分页 + 启停 + 密码重置。关联 `ParkingLot`（多对多，sys_admin_account_parking_lot）实现车场级数据权限。

**表**：`sys_admin_account`、`sys_admin_account_parking_lot`、`sys_admin_account_role`

### 1.4 自定义角色 + 权限矩阵

**设计**：每角色关联一组权限（sys_role_permission），权限标识格式 `模块:动作`（如 `fee:write`、`parking:read`）。Controller 方法用 `@RequirePermission` 注解声明所需权限，AOP 切面在请求前校验。

**实现**：`CustomRoleController` → `/api/v1/custom-roles`，`RequirePermissionAspect` 切面拦截注解。

**表**：`sys_role`、`sys_role_permission`、`sys_permission`

### 1.5 公司/集团 + 部门管理

**设计**：树形组织架构，公司含多个部门。`Company` 在遗留 `system.entity` 包中（唯一未迁移类）。部门为标准 CRUD。

**实现**：`CompanyController` → `/api/admin/companies`，`DepartmentController` → `/api/v1/departments`。树形返回时自动构建父子关系。

**表**：`company`、`sys_department`

### 1.6 高风险操作审计

**设计**：AOP 切面记录所有敏感操作（开闸、费用减免、车辆删除等），存储操作人、操作时间、IP、入参。

**实现**：通过 `@Log` 注解或 Auditable 接口标记，`AuditLogAspect` 记录。

**表**：`sys_audit_log`

### 1.7 系统参数

**设计**：多级参数体系——系统级（sys_config，全平台通用）和车场级（parking_lot_param，按车场覆盖）。

**实现**：`SystemParamController` → `/api/v1/system-params`，按 group 分组管理。车场参数在 ParkingManage 页面维护。

**表**：`sys_config`、`parking_lot_param`

### 1.8 文件上传

**设计**：统一文件上传接口，返回文件 URL。用于车牌图片上传等场景。

**表**：无独立表，文件存本地或 OSS（取决于配置）

## 二、停车场与设备档案

### 2.1 停车场 CRUD

**设计**：停车场为业务核心锚点，关联车道、计费规则、设备。含总车位数、状态（启用/停用/维护）。停车场的 `tenant_id` 决定了数据可见范围。

**实现**：`ParkingLotController` → `/api/admin/parking-lots`，含分页、详情、创建、更新、删除、容量检查（`capacity-check`）。返回 VO 含关联车道和设备统计。

**表**：`parking_lot`

### 2.2 车道管理

**设计**：每条车道属于一个停车场，有方向（entry/exit）、状态、序列号。**控闸设备**通过 `gate_device_id` 显式指定——优先使用车道级配置，未配置则 fallback 到设备型号的 `capabilities` 字段。

**实现**：`ParkingLaneController` → `/api/admin/lanes`。车道-设备绑定通过 `lane_device_binding` 表管理。

**表**：`parking_lane`、`lane_device_binding`

### 2.3 设备台账 CRUD

**设计**：设备归属厂商（device_vendor）+ 型号（device_model），有唯一序列号（SN）。含网络参数（IP/端口）、识别参数（车牌颜色过滤等）、显示/语音/语音播报模板配置。

**实现**：`DeviceController` → `/api/admin/devices`。`DeviceService` 负责设备命令下发（语音/显示/开闸等），通过 `resolveGateDevice(laneId)` 解析实际控闸设备（车道优先级）。前端 DeviceManager.vue 为三标签布局：识别联动 / 设备参数 / 手动测试。

**表**：`device`、`device_vendor`、`device_model`、`device_status_snapshot`、`device_command_audit`

### 2.4 设备显示屏参数

**设计**：设备可配置显示屏的字体颜色（displayTextColor）、旋转模式（displayRotateMode）、亮度（displayBrightness）、音量（displayVolume）。前端在设备编辑页「设备参数」标签下管理。

**实现**：`UpdateDeviceRequest` 含这四个字段，更新时持久化到 device 表。`DeviceVO` 查询时一并返回。

**迁移**：V20260906016

### 2.5 设备语音参数

**设计**：设备音量和男女声配置。

**实现**：`VoiceControlRequest` 含 `voiceVolume`（0-100）、`voiceMale`（boolean）。`DeviceService.voiceControl` 读取设备配置并下发到 DA。

**迁移**：V20260906017

### 2.6 识别联动（语音 + 显示屏自动播报）

**设计**：设备识别到车辆后自动语音播报 + 显示屏文字，分入场/出场两套模板。模板存储在 device 表中（6 个字段），支持 `{plate}` 和 `{type}` 占位符。前端编辑页「识别联动」标签提供垂直卡片布局 + 实时预览。

**实现**：
- 模板：`voice_entry/exit_welcome_template`、`display_entry/exit_welcome_template`、`voice_forbidden_template`、`display_forbidden_template`
- `DeviceWebhookService.triggerAutoVoiceAndDisplay(event, direction)` 根据方向选择模板，替换 `{plate}` 和 `{type}` 后下发语音/显示命令
- `vehicleTypeLabel()` 辅助方法将类型枚举转为中文标签

**迁移**：V20260906014 + V20260906018

## 三、设备接入服务（device-access）

### 3.1 架构

**设计**：独立 JVM 进程，通过 MQTT 连接 EMQX 与相机通信。识别事件等通过 HTTP Webhook（HMAC 签名）推送到 parking-system。七个子模块：
- `api`：接口定义（DeviceAccessClient 接口）
- `adapter`：品牌适配（臻识C5、芊熠、信路通）
- `common`：工具 / DTO
- `event`：事件引擎 / MQTT 消息路由 / EventOutbox 重试
- `mqtt`：MQTT 客户端封装
- `registry`：设备注册/心跳/状态管理
- `starter`：启动模块

### 3.2 臻识（C5）相机

**适配状态**：✅

**上行**：MQTT 主题订阅识别事件 / 心跳 / 状态上报。识别事件含图片 OSS URL。
**图片处理**：`RemoteImageDownloader` 在事件到达时异步将 OSS 图片下载到本地存储。
**主动抓拍**：`POST /api/v1/devices/{sn}/capture` → 下发 MQTT snapshot 命令 → 两段式（先收到 snapshot 响应，再等识别事件带图片 URL）。
**命令下发**：开闸/关闸/常开/显示/语音通过 MQTT 下行。

### 3.3 芊熠相机

**适配状态**：✅

**上行**：MQTT 协议，注册/心跳/识别/iooutput（开闸状态反馈）/常开/对时/RS485 透传。
**图片**：识别图片经独立 HTTP 接口 `/api/v1/images/upload` 上传，Nginx 反代到 device-access。
**SN 处理**：自动小写规范化（设备上报大写的 SN）。

### 3.4 信路通相机

**适配状态**：⚠️ 基础框架已搭建，MqttService 监听了 `xinlutong/#` 主题，`XinlutongDeviceCoordinator` 存在但核心适配逻辑未完成。主动抓拍（`capture`）仍为桩。

### 3.5 识别事件流程

```
相机识别 → MQTT 上行 → adapter 解析 → EventOutbox
→ HTTP Webhook POST /api/v1/device-webhook/events（HMAC 签名）
→ DeviceWebhookService.persistEventLog()（幂等去重，存 recognition_event_log）
→ BoothMonitorService.handleRecognition() 异步处理业务
```

## 四、岗亭作业

### 4.1 识别事件全自动处理

**设计**：Webhook 入口接收事件后，调用 `RecognitionEventService.processEvent()` 执行完整自动链路：
1. 根据设备 SN 查车道 → 判断方向（entry/exit）
2. 车牌号大写规范化
3. `VehicleTypeDecisionService` 判定车辆类型（黑名单→超级车牌→VIP→月租→储值→免费→临时）
4. **入场**：检查重复入场 → 创建 `parking_session` → 计算余位 → 开闸 → 写 `GateOperationLog` → 语音/显示屏播报 → WebSocket 推送到岗亭
5. **出场**：查在场 session → `FeeCalculationService` 计费（已切换，优先读入场快照） →（免费车直接开闸/收费车待确认）→ 关闸 →写日志 → WS 推送

**关键类**：`RecognitionEventService`、`VehicleTypeDecisionService`、`BoothWebSocketPublisher`、`GateOperationLogService`

### 4.2 人工开闸

**设计**：岗亭操作员通过车道列表的「开闸」按钮直接开闸。流程：自动抓拍当前画面 → 写操作日志（operator + time + lane + image）→ 下发开闸命令 → 超管兜底(`tenantId=null → tenantId=1`) → WebSocket 推送到岗亭。

**实现**：`RecognitionEventController.manualOpenGate(laneId)` → `RecognitionEventService.manualOpenGate()`。三步骤：抓拍（entry 车道用`manualCapture(laneId)`）→ 记录日志 → 开闸。支持多设备类型（臻识/芊熠）。

### 4.3 人工放行（Manual Release）

**设计**：独立弹窗，非识别到车牌的车辆可通过人工放行出入场。左右布局：
- 左侧：车牌输入（a-input + 小键盘）、计费区域（入口无、出口有免费/收费选项）、放行原因下拉
- 右侧：PlateTag 显示、车牌颜色（自动识别）、车辆类型（自动匹配，禁用不可手动选择）、抓拍按钮

**实现**：`ManualReleaseModal.vue`。键盘使用 `v-if` 控制显隐，省份简称（29个）+ 字母（A-Z 不含I/O）+ 数字（0-9）。`queryVehicle` API 自动匹配车辆类型（查 `sys_vehicle` 表），匹配失败默认临时车。

**后端**：`RecognitionEventController.manualEntry(ManualEntryCmd)` / `manualExit(ParkingSessionExitCmd)`。入口补充手动入场记录和日志；出口补充 `exitImage` + `exitOperator` 写入 session。

### 4.4 关闸 / 常开锁定 / 取消常开

**设计**：岗亭操作员可临时锁定道闸为常开状态（如高峰期），或取消常开恢复自动模式。

**实现**：`RecognitionEventController.manualCloseGate` / `lockOpenGate` / `unlockOpenGate` → `DeviceService` 下发对应命令。锁定状态通过 `gate_status` 字段跟踪。

### 4.5 手动抓拍

**设计**：严格按入口车道相机抓拍，臻识走 MQTT snapshot 两段式（下发→等结果→OSS下载落盘），芊熠走 `snapshot` 优先 / `tarkphoto` 回退。

**实现**：`BoothRecognitionController.manualCapture(laneId)` → 相机适配器。

### 4.6 余位调整与实时推送

**设计**：岗亭端实时显示总车位/已用车位/剩余车位。支持直接设置剩余车位数（SET模式）。每次开闸/关闸后自动重新计算（总数 - 在场数量）并 WebSocket 推送。

**实现**：
- `BoothSpaceController.adjustSpace` → `BoothSpaceService` 直接 SET
- `BoothWebSocketPublisher.pushSpaceUpdate(tenantId)` 计算并广播
- 前端 `monitor.ts` store 监听 WebSocket 更新

### 4.7 费用减免

**设计**：岗亭操作员可为在场车辆减免费用，需独立权限 `fee:reduce`，操作全程记录到审计日志。

**实现**：`BoothFeeReductionController` → `POST /api/v1/booth/charge/fee-reduction`。

### 4.8 交接班

**设计**：岗亭管理员上下班交接，记录当班期间的现金收款、减免总金额、操作次数。

**实现**：`ShiftRecordController` → `/api/v1/shift-records`，含开班/交班/当班查询/现金订单汇总。

**表**：`shift_record`

### 4.9 收费面板（Charge Panel）

**设计**：出场车辆自动弹出收费面板，显示车牌、入场时间、停车时长、费用。操作员可确认收费（目前为模拟支付，直接开闸）或减免。

**实现**：`ChargePanel.vue`。模拟支付逻辑：点击确认→调用 `mockPaymentRecord` 接口→标记支付→开闸。

### 4.10 岗亭监控 WebSocket

**设计**：服务端主动推送岗亭需要的实时状态更新：
- 剩余车位变化（pushSpaceUpdate）
- 道闸状态变化（pushGateStatus）
- 新识别事件（pushNewEvent）
- 在场车辆更新

**实现**：`BoothWebSocketPublisher`（Spring Bean），使用原生 WebSocket 按 tenantId 分组广播。前端 `websocket.ts` 自动重连。

## 五、车辆管理与固定车

### 5.1 车辆主档 CRUD

**设计**：车辆主档记录车牌号、车辆类型（MONTHLY/VIP/FREE/PREPAID/FIXED/BLACKLIST/TEMP）、车主信息、生效车道（laneIds）、有效期（月租/固定车）、储值余额。完全兼容租户隔离。

**实现**：`SysVehicleController` → `/api/v1/vehicles`。创建/更新时需校验车道权限。批量删除走逻辑删除（deleted_at）。

**表**：`sys_vehicle`

### 5.2 车辆类型判定引擎

**设计**：优先级链——**黑名单 > 超级车牌 > VIP > 月租（有效期内）> 储值（余额>0）> 免费 > 临时车**。车辆类型决定入场后的计费策略和出场时的收费行为。

**实现**：`VehicleTypeDecisionService`。被识别链路（RecognitionEventService.processEvent）和车辆管理页调用。

### 5.3 一位多车绑定

**设计**：一个月卡/固定车位允许绑定多个子车牌（如夫妻车），任一车牌触发识别即消耗一次月卡额度。

**实现**：`SysVehicle.multiPlates` 字段 + `sys_vehicle_multi_plate` 表。

### 5.4 车辆资料审核

**设计**：车主提交车辆资料后，平台管理员审核通过方可生效。

**实现**：`VehicleAuditController` → `/api/v1/vehicle-audits`。

**表**：`vehicle_audit`

### 5.5 黑白名单 CRUD

**设计**：独立的黑白名单体系，与车辆类型判定引擎联动。支持触发类型配置（入场/出场/全部）。

**实现**：`VehicleListController` → `/api/v1/admin/vehicle-list`。

**表**：`vehicle_list`

### 5.6 储值车钱包

**设计**：储值车有独立钱包，支持充值/退款/调账，每次交易记录流水。出场时自动从余额扣除停车费。

**实现**：`VehicleWalletController` → `/api/v1/vehicle-wallets`。月租过期自动转为储值消费（当余额>0时），在 `VehicleTypeDecisionService` 中处理。

**表**：`sys_vehicle_wallet`、`sys_vehicle_wallet_log`

### 5.7 月卡/固定车续费闭环

**设计**：车主可自助发起续费→生成订单→支付回调→回写有效期。幂等设计（防止重复支付）。

**实现**：`VehicleRenewalService` → `/api/v1/vehicles/{id}/renew*`。支付回调通过 `PayCallbackService` 统一处理，对同一笔续费订单只处理一次。

**表**：`vehicle_renewal_log`（复用 order 体系）

### 5.8 白名单同步到设备

**设计**：车辆创建/更新/删除时，自动将白名单（车牌号 + 有效期的固定车）同步到下游设备（相机本地白名单），实现离线识别。

**实现**：`DeviceWhitelistSyncService` 监听 `SysVehicleService` 变更事件，调用 `DeviceAccessClient.syncWhitelist` 下发。目前 DA 侧 `syncWhitelist` 仅打日志（DA 未实现白名单协议）。

## 六、计费体系

### 6.2 新计费规则（FeeRule）

**状态**：✅ **CRUD/配置入口已启用**；✅ **A1–A5 完成：4 个关键列、版本历史、计算补全、入场快照、识别链路与 H5 切换均已落地**

**设计**：4 种计费模式——按时、按次、阶梯、分时段。支持免费时长、首时段、每日封顶、跨天规则（自然日 / 连续24h）。优先级：区域 > 车场 > 平台默认。规则可绑定到停车场（`parking_lot.fee_rule_id`）和车辆（`sys_vehicle.fee_rule_id`）。支持按车辆类型、车牌颜色的维度差异化计费。已补齐 `first_period_minutes`、`max_amount`、`cross_day_mode`、`effect_mode`，并新增版本历史表 `fee_rule_history` 与入场快照。

## 十三、已知生产环境问题

> 以下问题是在 2026-07-26 检查服务器日志时发现的：

| # | 问题 | 日志证据 | 影响 |
|---|---|---|---|
| 1 | **`recognition_event_log.plate_number` 无默认值** | `java.sql.SQLException: Field 'plate_number' doesn't have a default value` | 非识别事件（如人工开闸、常开锁定）写入 event log 时报错，导致部分日志丢失 |
| 2 | **EventOutbox 为直推模式** | DA 日志中 `t_event_outbox` 查询 `PENDING` 返回 0 条 | 识别事件没有被 outbox 持久化，DA 重启时可能丢失未推送的事件 |
| 3 | **actuator/health 外网 403** | `curl http://<SERVER_IP>/api/actuator/health` → 403 | Nginx 安全策略正确：仅内网可访问 Actuator。外部监控需走 SSH 隧道或配置内网探针 |
